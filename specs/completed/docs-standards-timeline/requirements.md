# Requirements: docs-standards-timeline

> **Purpose:** Define what the change must do. Written in Plan mode before design. Must be approved via AskQuestion `requirements-review` popup before proceeding to design.

## User Stories

| ID | As a ... | I want to ... | So that ... |
|----|----------|---------------|-------------|
| US-1 | AI agent | Every doc under `docs/` to have consistent YAML frontmatter + template structure | I can machine-parse status, owner, category, and last_verified without reading the full body |
| US-2 | AI agent | A unified timeline aggregating all `docs/changes/*/CHANGELOG.md` entries | I can quick-glance the entire project history and understand what changed, when, and why |
| US-3 | Human developer | A clear standard enforced on all docs (frontmatter + structure) so new docs are consistent | I and future agents follow the same conventions and nothing is orphaned |
| US-4 | AI agent | The `docs/INDEX.md` manifest to accurately reflect ALL docs (including subdirectories) with status and last_updated | I can discover every doc, its purpose, and its freshness at a glance |
| US-5 | AI agent | Clear lifecycle metadata on every doc (active, archived, draft, obsolete) | I can quickly filter what is current vs. stale |

## Acceptance Criteria (EARS format)

> EARS = Easy Approach to Requirements Syntax: "When {condition}, the system shall {behavior}".

| ID | Criterion |
|----|-----------|
| AC-1 | When a doc exists under `docs/` (including subfolders), it SHALL include YAML frontmatter with `status`, `last_verified`, `category`, and `owner` fields |
| AC-2 | When a doc exists under `docs/`, it SHALL follow the standardized template structure: `# Title` → purpose blockquote → `## Related` → `## Last updated` |
| AC-3 | When a new `docs/changes/*/CHANGELOG.md` entry is added, the system SHALL have a unified timeline doc that aggregates all entries chronologically |
| AC-4 | When `docs/INDEX.md` is updated, it SHALL list every doc under `docs/` (recursively) with `status`, `last_updated`, and `category` |
| AC-5 | When a doc is archived or becomes obsolete, its frontmatter `status` SHALL reflect that (e.g., `archived`, `obsolete`) — the doc is not deleted |
| AC-6 | When the standard changes in the future, the `docs/standards/documentation.md` SHALL be updated as the single source of truth for the standard |
| AC-7 | When all changes are complete, every existing doc in `docs/` SHALL be audited and updated to conform to the new standard |
| AC-8 | When `docs/CHAT_PROTOCOL.md` is audited, the server→client `message` event type SHALL be corrected from `"message"` to `"assistant.message"` to match src/api/server.py, and ghost events (`token_budget_update`, `cloud_budget_warning`) SHALL be removed or annotated as unimplemented |
| AC-9 | When `docs/STATUS.md` is audited, the bug status table SHALL be reconciled with BUG-TRACKER.md — BUG-1 through BUG-8 SHALL reflect their actual fixed state per code evidence |
| AC-10 | When `docs/API_REFERENCE.md` is audited, all 13 missing endpoints SHALL be added, including `/v1/chat/completions`, persona CRUD (`/api/persona`, `/api/personas`), project knowledge endpoints, and chat title generation |
| AC-11 | When `docs/ARCHITECTURE_OVERVIEW.md` is audited, the graph flow diagram SHALL be updated to include `auto_summarize`, `scope_clarify`, and `plan_review` nodes matching git status in `src/agent/graph.py` |
| AC-12 | When `docs/AI_AGENT_INDEX.md` is audited, the phase status SHALL be updated to include Phase 8 and the bug table SHALL include a status column reflecting actual fix state |
| AC-13 | When `docs/INDEX.md` is audited, it SHALL either expand to list all docs (not just SDD framework), or its description SHALL clarify it is a selective SDD manifest |
| AC-14 | When `docs/TOOLS.md` is audited, `search_workspace_docs` SHALL be added to the `memory` toolbox section |

## Non-Functional Requirements

| ID | Category | Requirement |
|----|----------|-------------|
| NFR-1 | Maintainability | The unified timeline SHALL be auto-generated by an agent task, not manually maintained |
| NFR-2 | Discoverability | The `docs/README.md` and `docs/INDEX.md` SHALL point to the unified timeline |
| NFR-3 | Scalability | The standard SHALL be simple enough that updating 50+ docs is feasible in a single SDD change |
| NFR-4 | Consistency | All docs SHALL use the same frontmatter fields — no optional fields with different names |

## Edge Cases and Error States

- What happens when a doc has no CHANGELOG entries to aggregate → timeline section shows empty state
- What happens when frontmatter fields are missing → validator or manual audit catches it
- What happens when a doc is in archive/ and not actively used → status is `archived` per AC-5
- What happens when two changes have the same date in the timeline → sort by timestamp or slug

## Out of Scope

- Automating frontmatter validation via CI hook (may be a follow-up change)
- Moving or deleting existing docs — only adding metadata/structure and correcting sync errors
- Rewriting doc body content beyond the correction of doc–code mismatches listed in AC-8 through AC-14
- Restructuring `src/` code to match docs (docs should match code, not vice versa)
- Team settings, collaborators, or multi-user configuration — project is single-contributor

## Dependencies

- `docs/` directory with all existing files
- `docs/changes/*/CHANGELOG.md` files for timeline aggregation
- `docs/standards/documentation.md` — will be updated as the canonical standard
